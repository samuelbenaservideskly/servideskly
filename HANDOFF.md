## 1. What this is, in five lines

A self-hosted helpdesk / service desk. Node 24, TypeScript (ESM, strict),
Express 4, server-rendered EJS, **SQLite or PostgreSQL** (one SQL, two
drivers). Client JavaScript is an **explicit list of eight exceptions**
(CLAUDE.md has the table); every other response is `script-src 'none'`.
Requesters raise tickets through forms (templates); technicians work queues
and dashboards; administrators configure everything under **Settings** in the
UI, not in environment variables.

**There are two repositories.** This one is the helpdesk. Beside it,
`C:\Temp\Ticketing system - Customer portal` is the storefront a customer
orders a hosted helpdesk from, and the worker that provisions it on Azure.
See **section 9**.

## 2. Run, test, build

```bash
npm install
npm run dev          # http://localhost:3000, tsx watch, runs migrations on start
npm run verify       # typecheck (src + tests) + 964 tests + npm audit
npm run build        # compiles to dist/ - npm start runs dist, NOT src
npm run demo:seed    # builds data/demo.sqlite: 5 companies, 5 groups, 75 days of tickets
npm run dev:demo     # that database on port 3001
```

- Sign in as **`admin@local`** / `1234` (or `user@local` / `1234`). There are
  no usernames; the email is the sign-in name.
- **The owner runs their own `npm run dev` on port 3000.** Use the demo on
  3001, or `.claude/launch.json`'s `helpdesk-preview` on 3100, rather than
  taking their port.
- **Restart after editing `public/css/app.css` or anything in `public/js`.**
  The asset cache version is hashed once at start-up and `tsx watch` does not
  watch them. A restart also signs you out.
- `npm start` runs the **compiled** `dist/`. If `src` changes and `dist` is
  not rebuilt, the server runs old code against new views. Prefer `npm run dev`.
- **PostgreSQL**: set `DATABASE_URL=postgres://...` and it runs there instead
  of SQLite. CI runs the whole suite on both. Tests on PostgreSQL need
  `TEST_PG_ADMIN_URL` (a database per test file).
- **After adding a migration**: `npx tsx scripts/pg-schema.ts` regenerates
  `src/db/pg-schema.ts`, or `tests/pg-schema.test.ts` fails.

## 3. How the code is laid out

```
src/
  app.ts               middleware order matters; CSRF exemptions for multipart
  server.ts            start-up order, timers (outbox, auto-close, SLA, mail poll)
  config.ts            environment, fails closed
  settings/index.ts    the runtime settings document (one JSON row), cached
  db/index.ts          query/execute, transactions, toPostgres(), BOOLEAN/JSON_COLUMNS
  db/migrations.ts     forward-only; NEVER edit a shipped one, append
  db/pg-schema.ts      GENERATED by scripts/pg-schema.ts - do not hand-edit
  lib/                 format (Locale-aware dates), time-zones, csv, xlsx,
                       secret-box, audit, errors, colour, logger
  auth/                oidc (Entra/Google/Okta/generic), local-accounts,
                       sign-in-codes, password-reset, registration,
                       setup-token, provisioning (JIT), session-store
  middleware/          security headers and CSP, csrf, sessions, theme,
                       view-locals, select-search
  routes/              one router per area; settings.ts mounts the settings ones
  services/            the logic; routes stay thin
views/                 EJS; admin/settings/* render inside _layout.ejs
public/css/app.css     the one stylesheet (append-only sections at the end)
public/css/fonts.css   GENERATED @font-face rules - see scripts/get-fonts.cjs
public/fonts/          the six licensed fonts, each with its OFL.txt, and
                       NOTICES.md recording licence, source and checksum
public/js/             the six approved scripts (see CLAUDE.md's table)
scripts/               demo-data.ts, pg-schema.ts, get-fonts.cjs
tests/                 80 files, node:test + supertest; one database per file
.github/workflows/     ci, deploy-customer, promote-release, check-azure,
                       customer-log, customer-secrets
```

Key helpers to reuse rather than reinvent:

| Need | Use |
| --- | --- |
| Render any settings page | `settingsView(section, extra)` (routes/settings-shared.ts) |
| A write that may be refused | `attempt()` (routes/form-errors.ts) - re-renders the form, never a 409 page |
| A refusal beside its control | `flash(req, type, msg, where)` |
| A create form | a `:target` dialog behind a `+ New ...` primary button |
| A removable table row | `partials/bin-button.ejs` (disabled with the reason when protected) |
| Back to a list | `partials/back-link.ejs` |
| An explanation | `partials/info.ejs` (the ⓘ) |
| A settings gear | `partials/icon-gear.ejs` |
| An icon | `partials/icon.ejs` (inline SVG by name) |
| Dates in a view | `formatDateTime()` / `formatDate()` - Locale-aware |
| A searched, paged list | `_list-search.ejs` + `_list-pages.ejs`, filtered in SQL |
| Members of a group | `_member-picker.ejs` (two tables, paged, `setMembersWithin`) |
| A person's display name | `applyDisplayName()` after any write of their names |

Agreed for later (17 Oct 2026), **before anybody runs more than one instance**
of a helpdesk - a B1 plan is one instance and needs none of it:

- **Settings and languages** are cached per process (`settings()`, the
  language cache): a change made on one instance must reach the others -
  PostgreSQL LISTEN/NOTIFY on save, or a short re-check of `updated_at`.
- **Rate limits** (sign-in, API keys, hooks) count per process: store them in
  PostgreSQL so they count across instances.
- **Background jobs** run on every instance: the outbox sender
  (`flushOutbox`, single-flight only within a process - two instances would
  send the same mail twice), mail polling, the hourly and 15-minute sweeps.
  One at a time across instances: an advisory lock per job, or a row claim.
- **Attachments** are files on one instance's disk (`UPLOAD_DIR`): move them
  to Blob Storage, as section 6 already intends.

## 6a. Automation - the agreed design (built; kept for the reasoning)

- **Where**: Settings - Advanced - Automation. A list (name, trigger, on/off,
  last run) with a `+ New automation` dialog; each opens an editor.
- **Model**: `automations(id, name, is_enabled, trigger, graph JSON, ...)` and
  `automation_runs(...)` for the log. `graph = { nodes: [{id, type, x, y,
  config}], edges: [{from, pin, to}] }` - execution wires only; a node's
  settings are fields on the node, not data wires.
- **Node types**: one trigger (Ticket created, Status changed, Priority
  changed, Assigned, Comment added, SLA breached, An HTTP request is received);
  *If* (field, operator, value; True/False out-pins); actions: Send
  notification, Set status, Set priority, Route to group, Assign to technician,
  Add comment, Send (authenticated) HTTP request, Create a ticket, Create a
  template, Create a notification, Attach the files from the request.
- **Engine** (`services/automation.ts`): `onEvent(trigger, ticketId)` from the
  existing trigger points; walks from the trigger along wires, bounded by
  MAX_STEPS; actions done by an automation must not re-trigger automations;
  every run audited and logged. Ones that call out run in the background.
- **Editor without a script first** (house rule): step cards with their forms,
  an "Add action" dialog, ticked targets to wire. Every change is a form POST
  and a redirect.
- **Canvas on top** (`automation-canvas.js`): drag a box to move it, drag from
  an output dot to wire it. Each gesture ends in a **form submit**, exactly as
  form-builder.js does - no fetch, `connect-src` stays `'none'` there.

## 7. Things to know before touching code

- **Read CLAUDE.md "Traps that have already bitten"** - positional `?`
  placeholders, heredocs mangling source, ESM circular imports, settings shell
  locals, `attempt()`, CSS class collisions, `<%= %>` cannot build an attribute.
- **Never write source with shell heredocs or `node -e`** when the text has
  backslashes, backticks or quotes. They have been silently eaten several
  times (a regex lost `\p`, CLAUDE.md lost names in backticks). Use the
  Write/Edit tools, or write a `.cjs` patch file with Write and run that.
- **No new client script without the owner's approval.** CLAUDE.md has the
  table of eight; adding a row is the owner's decision, not the agent's.
- **No em dashes** anywhere - UI, comments and documents alike. Plain hyphens.
- **Check a file does not exist before writing a new one.** A session once
  overwrote `tests/automation.test.ts` with a new file of the same name.
- In tests, prefer **static imports**: a dynamic `import()` under tsx once
  loaded a second copy of the settings module and hid an update.
- A test that expects mail to be queued must **create a mailbox or relay**
  first; without one nothing is queued, and that is correct behaviour.
- **Things SQLite allows and PostgreSQL refuses** are listed in CLAUDE.md
  ("SQLite or PostgreSQL"). CI catches them; knowing them saves the round trip.
- `src/routes/accounts-admin.ts` is **dead code** (not mounted). It compiles.
  This is a git repository now, so deleting it is safe and reversible.
- The local database's **"Please approve this request"** notification may still
  carry the old wording ("anybody with the link can answer"). New installs get
  the new text; an existing one is edited under Mail - Notifications.

## 9. The customer portal (the other repository)

`C:\Temp\Ticketing system - Customer portal` - a **separate app and a separate
git repository** (branch `main`). Express, TypeScript, PostgreSQL, no ORM and
no client script. Its own `README.md` and `AGENTS.md` are the detail; this is
the shape of it. This repository's `.claude/launch.json` has a
`customer-portal` entry on port 3200 for running it beside the helpdesk.

**What it does.** A client signs in with Microsoft, orders a helpdesk from a
storefront, and a background worker builds it on Azure:

```
register -> Microsoft Entra External ID sign-up page (our customers' own directory)
sign in  -> OpenID Connect (PKCE) against that directory

order -> queued -> worker (src/steps.ts): resource group, PostgreSQL database
         and login, two Key Vault secrets, B1 Linux plan and a Node 24 web app
         with a managed identity, that identity's vault access, app settings as
         Key Vault references, deploy through GitHub Actions
      -> starting -> /readyz answers 200 -> ready
      -> "Set up your administrator account" (a one-time signed link)

cancel -> teardown: vault access, resource group, database and login, secrets
          purged -> cancelled, the address free again
```

**How the two repositories meet:**

- **Release channels.** Production and Development, each a branch **in this
  repository** (`production`, `development`); the tags `stable` and
  `previous` are no longer used (16 Oct 2026). The portal orders production
  (the choice is switched off in its order form). The worker starts
  `deploy-customer.yml` here with `app_name` and `channel`.
  `promote-release.yml` ("Promote to production") moves `production`
  forward. Promoting does not redeploy anybody.
- **The setup link.** `POST /orders/<id>/admin-setup` in the portal signs a
  token with **the helpdesk's own session secret** (read from Key Vault) and
  redirects to `https://<name>.azurewebsites.net/setup?t=...`, which
  `routes/admin-setup.ts` and `auth/setup-token.ts` answer here. The
  double-click fix (section 5, item 50) was found through this path.
- **Hosted helpdesks run on PostgreSQL**, with `UPLOAD_DIR=/home/data/uploads`
  on App Service's persistent `/home`.

**Known gaps there, before a real customer** (its README has the full list):
attachments are files on the web app's `/home` rather than Blob Storage;
application logging is not switched on for customer web apps; there is **no
payment step** by request; the worker runs inside the web app one order at a
time; and customer web apps should be created in the database server's region.

**Prices are samples** while `SAMPLE_PRICES` is true, every page that shows one
says so, and checkout is an order submission, never a payment.
